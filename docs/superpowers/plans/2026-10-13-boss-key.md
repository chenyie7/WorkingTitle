# 老板键 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在设置里导入一份纯文本工作文档，之后按一条快捷键就能把阅读区从小说切到那份文档、再按一下切回来。

**Architecture:** 工作文档做成**第二本 `Novel`**，走同一个 `TypingEngine`。`App` 里从「一对（novel, engine）」变成「两对 + 一个 `bossMode` 布尔」，渲染树只认一个「当前显示的那份」。工作文档不落盘（不写 novel-cache、不写 session），每次进入老板模式按「铺满量」重铺。

**Tech Stack:** Electron 44 + electron-vite / React 19 / TypeScript 5.9 / vitest + jsdom / pnpm

```ts
/**
 * 老板键的「铺满量」：把「一页」折算成多少字，以及那个百分比的夹紧与步进。
 *
 * 【为什么单开一个模块】它是纯计算，与引擎、设置、界面都无关。塞进 `types.ts` 会让那个
 * 文件继续长下去，塞进 `engine.ts` 会把「怎么显示」混进「抽字的规则」——而 `engine.ts`
 * 是全项目唯一那条核心不变量的所在地，那里每多一个概念都要多想一次。
 */

/** 铺满百分比的取值范围，单位是「一页的百分之几」。 */
export const BOSS_FILL_MIN = 0
export const BOSS_FILL_MAX = 100
/** 两条增减快捷键每按一次的步进。 */
export const BOSS_FILL_STEP = 10

/**
 * 一页约多少字。
 *
 * 推导（对着 `src/renderer/src/styles/page.css` 的 `.wt-page` 算）：
 *   纸张宽 794px，左右 padding 各 84px → 正文宽 626px；
 *   字号 15px → 每行约 626 / 15 ≈ 41.7 字；
 *   纸张 min-height 1080px，上下 padding 72 / 96px → 正文区 912px；
 *   行高 1.9 × 15px = 28.5px → 32 行；
 *   32 × 41.7 ≈ 1334，取 1330 —— 恰好铺满一整张纸（72 + 912 + 96 = 1080，纸不会长高）。
 *
 * 【它量的是「一页」，不是「一屏」——这两个数差得不小】可见区比一页矮得多：`.wt-canvas`
 * 的可见高度实测 667px，而一页正文要 912px。所以 100% 时纸的上边沿落在视野之外，画面是
 * 一整窗连续的字——那正是老板键要的样子，像「你正在一份文档中间」，而不是「光标正好停在
 * 页首」。想让纸的上边沿露出来，往 60% 以下调（不滚动的条件是光标底边离画布下沿还留着
 * `CARET_MARGIN` 24px，算下来约 59.7%）。
 *
 * 【它是约数，不是测量值】字号、纸张尺寸、行高任何一个改了它都会失准；中英混排时的实际
 * 行宽也与 41.7 有出入。校准它的手段是老板键铺满那两条 +/- 快捷键，**不是改这个常量**。
 *
 * 性质与 `RENDER_WINDOW_LIMIT` 同类：一个写在 core 里的经验常量。
 */
export const CHARS_PER_SHEET = 1330

export function clampBossFillPercent(n: number): number {
  // 【非有限值落到满页，而不是 0】它来自「设置文件被改坏 / 字段缺失」。落到 0 那个退化
  // 边界的话，老板键切过去是一片空白——那正是这个功能要避免的画面。与 `clampRatio` 对
  // NaN 的处理同一姿态：不可用的输入给一个「能用」的默认值。
  if (!Number.isFinite(n)) return BOSS_FILL_MAX
  return Math.max(BOSS_FILL_MIN, Math.min(BOSS_FILL_MAX, Math.round(n)))
}

/** 步进一档。**两端夹住、不循环**——按到头再按没有反应，而不是跳回另一端。 */
export function stepBossFill(current: number, dir: 1 | -1): number {
  return clampBossFillPercent(current + dir * BOSS_FILL_STEP)
}

/** 百分比 → 该铺多少字，喂给 `TypingEngine.revealTo`。 */
export function fillCharsFor(percent: number): number {
  return Math.round((CHARS_PER_SHEET * clampBossFillPercent(percent)) / 100)
}
```

```ts
  /**
   * 把阅读光标直接设到 `n`，夹紧到 `[revealStart, total]`。**可增可减。**
   *
   * 老板键的「铺满」用它：切到工作文档时一次把设定好的那些字铺出来；按 +/- 调铺满量时又用它
   * 重铺。**对外的方法里只有它收的是绝对位置**——`pump` / `backspace` 收的是「走多少步」的
   * 相对量（还要乘上可变的 `ratio`），`jumpToChapter` 收的是章号、目标由 `chapterPos[i]` 决定。
   * 「铺到第 N 字」这种说法只能落到它身上。
   *
   * 【为什么走 commit 而不是自己改 `_state.cursor`】`commit` 是「统一收尾规则」的唯一实现：
   * 它会补上被整章越过的那些章，并把 `chapterPos[新章]` 同步成章内偏移。绕开它自己设游标，
   * 跳章后的侧栏高亮与 `chapterPos` 就会与游标脱节——而那种脱节不会抛错，只会表现为
   * 「进度莫名其妙不对」。
   *
   * 【下界为什么是 revealStart 而不是 0】与 `backspace` 同一个理由：阅读区显示的是
   * `flatText.slice(revealStart, cursor)`，游标退到窗口起点之前，阅读区就永久空白了。
   *
   * 【非有限值必须在这里挡掉】`Math.min(NaN, total)` 与 `Math.max(revealStart, NaN)` 都返回
   * NaN，一路传进 commit 之后游标就是 NaN——`visibleText` 变空串、状态栏百分比变 NaN%，
   * 而且**再也恢复不了**（此后每一次 pump 都在 NaN 上算）。这不是理论风险：调用方拿的是
   * 「设置文件里的一个数字」。
   */
  revealTo(n: number): void {
    if (!Number.isFinite(n)) return
    // 游标是字符下标，收成整数再夹——否则 3.7 会透传进 toSession 与 slice
    const target = Math.round(n)
    const next = Math.max(this._state.revealStart, Math.min(target, this._novel.flatText.length))
    if (next === this._state.cursor) return
    this.commit(next)
  }
```

```ts
/**
 * 读一份**工作文档**。

 *    每次启动直接读，几十毫秒。
 * 2. **不抛异常，只返回 null**。文件读不出来（被移走、权限、EISDIR）是一条正常路径——

 * 3. **空文本判为不可用**。一份空文档放进来的话，老板键切过去是一片空白，等于没有。

function loadWorkDoc(filePath: string): Novel | null {
  if (typeof filePath !== 'string') return null
  try {
    const novel = loadNovelFromFile(filePath)
    return novel.flatText.length === 0 ? null : novel
  } catch (err) {
    console.warn('[wt] 读取工作文档失败：', filePath, err)
    return null
  }
}
```
