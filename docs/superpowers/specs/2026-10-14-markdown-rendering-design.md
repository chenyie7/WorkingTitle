# Markdown 渲染 —— 设计文档

日期：2026-10-14（2026-10-15 修订，见第 3.2 节与文末的修订记录）
状态：待用户审阅
分支：`feat/boss-key`（本功能直接在这条分支上继续开发，理由见第 17 节）

## 1. 目标

导入的 `.md` 工作文档现在按纯文本显示，正文里的 `#`、`**`、`|` 原样露在屏幕上，看起来不像一份真文档。本功能把它渲染出来：标题是标题、表格是表格、列表带项目符号。

要解决的问题仍然是**伪装**。老板键切过去之后，屏幕上那份东西得经得起看——一份摊着 `## 一、本季度进展` 的纯文本，和一份排版正常的文档，差别就在这里。

**范围：只作用于工作文档，且只作用于扩展名为 `.md` / `.markdown` 的那一路。** 小说（导入过滤器只收 txt）与 `.txt` 工作文档一个字都不变。

## 2. 现状

工作文档已经是「第二本 `Novel`」，由 `loadNovelFromFile` 读进来：解码 → 归一化换行 → `splitChapters` → `flatText`。阅读区显示的是 `flatText.slice(revealStart, cursor)` 这一个**字符串**（`Page.tsx` 的 `visibleText`）。

两件顺带确认的事：

- **小说那条路不可能出现 md。** `wt:import-novel` 的过滤器只有 `txt` 与「所有文件」，而「所有文件」是给无扩展名/异扩展名的**纯文本**留的口子，不是给 md 的入口。真正要防的是有人在小说那一路手动选一个 `.md`——那种情况下本功能**不生效**（判定按路径扩展名，而小说那一路不走渲染分支），显示的是原文。这与今天的行为一致。
- **md 工作文档的章节列表基本只有一章。** `splitChapters` 认的是「第 X 章」那类中文章节标记，`# 标题` 不在其列。老板模式下章节栏本来就是收起的（见老板键设计第 7 节），所以看不见；这里只是说明它不会因此坏掉。

## 3. 四条核心决策

这四条是「选了这条，别的都跟着变」的。每条都对应访谈里的一次拍板。

### 3.1 解析成带字符偏移的语法树，按偏移裁剪

用 `remark`（mdast）解析整份文档。mdast 的每个节点自带 `position.start.offset` / `end.offset`，就是**相对 `flatText` 的字符下标**——和 `cursor`、`revealStart` 是同一个坐标系，不需要任何换算。

于是「按字符揭示」这条既有机制直接变成「按偏移裁剪」：光标走到哪，哪些节点的文本被填上，是一个纯函数。

**为什么不把「已经抽出来的那一段」当独立 md 重新解析**（那样实现最省）：未闭合的记号会退化成字面文字，半截表格根本不成表格。它与下面 3.2 直接冲突，所以第一条就被否掉了。

### 3.2 结构预知（2026-10-15 修订：粒度从「块」下沉到「重复单元」）

**一个块只要有任何一个字符被揭示（起始偏移 < cursor），它就出现在屏幕上；还没开始的块一概不画。**

块**内部**的重复单元——**表格的行、列表的项**——各自按自己的起始偏移判：光标走到哪一行、哪一项，那一行/那一项才画出来。同一块里还没走到的行/项**只留出高度，不画任何外框**（不画网格线、不画项目符号、不画代码框底色）。

三处的具体表现：

| 元素 | 还没打字到 | 打到了、但文字还没出来 |
|---|---|---|
| 表格 | 行不存在，表格底部留出「默认一行高 × 剩余行数」的空白 | **整行**画出来（含这一行的全部单元格），格子是空的 |
| 代码块 | 框只包住已经揭示的行，剩下的行留「默认一行高 × 剩余行数」的空白 | — |
| 列表 | 项**完全不画**：没有符号，也不占高度 | 画符号（项目符号 / 序号 / 任务框），文字空着 |
| 行内（粗体、斜体、行内代码、链接） | 粒度**不下沉**，见下 | 照旧 |

**表格为什么是「整行」而不是「逐个单元格」**：一行里前面几个格子揭示、后面几个没揭示时，若按格判，最后那一行会缺几列，屏幕上的表格是**残的**。缺列比空格子难看得多，所以这一层只下到行。

**列表为什么完全不占位**：项目符号本身就是「这一项存在」的宣告，留一条空白的项比不留更怪。这与表格/代码块的选择不同，是刻意的——那两处的占位是**空白**，看不出「有东西没来」；列表的占位只能是一条带符号的空行，反而露馅。

**行内为什么不下沉**：3.4 那条「屏幕上永不出现裸记号」靠的正是「结构先于文字」。行内记号比它的文字更早被光标经过，若按行内的起始偏移判，`**季度**` 在抽到第二个 `*` 时会画出一个空 `<strong>`——屏幕上什么都没有，下一个字符却突然变粗，中间那一下就是「结构还没到」的破绽。

**代价：布局会跳。** 这条要写清楚，因为它是这次改动的核心取舍。结构预知最初选「整块画全」，图的就是**布局稳定**——整张网格一次到位，下面的内容不动。改成逐行之后，一个占位（默认一行高）在光标走到时变成真实高度，**它下面的内容就往下推一次**。留「默认一行高」只是把这一跳变小，消不掉。这是看到实际效果之后选择接受的。

**「跳」有两种，别混（2026-10-15 真机核过）**：**设计内的跳**是「一行一行地长出来」——每多揭示一行，下面推一行的高度，**这一种消不掉也不打算消**。另一种是**bug 的跳**：`.wt-md-pre` 的 `min-height` 写成一个边框盒的行高时，从「框里 0 个字」跨到「抽出第一个字符」会让下面整页**多跳 20px**（框自己的上下内边距），真机实测那一格整块高 39.0383 行、其余每一格都是 39.9999 行，差的 **0.9617 行 × 20.8 = 20.0px** 正是被 `box-sizing: border-box` 吃掉的那段 padding。

**占位与框的换算，真机核过**：占位高度恒等于「`clip.ts` 报的行数 × 20.8」（78 个采样格，最大偏差 0.006px，即 1/64px 量化）——**占位这一侧没有缺口**；而 `.wt-md-pre` 的 `min-height` 必须是**一个边框盒的行高**（`20.8 + 上下 padding 20 = 40.8`），写成 `20.8` 只补到 0.8px。修好之后「框内行数 + 占位行数 == 总行数」**在每一个光标位置都成立**（含「框里 0 个字」那一格，它应当是 40.00）。

**「块」的定义不变：mdast 根节点的直接子节点。** 保留还是丢掉、量高度、铺满切点、折叠切点仍然一律在这一层做。这次改的只是**块内部**的重复单元多了一道判据，块一级的规则一个字没动。

**「未揭示的行/项里一个未揭示的字符都不上屏」这条没有让步。** 占位只有高度，没有内容。

**两类叶子要分开判，这一条是实施时量出来才看得见的。**

- `image`、`footnoteReference`、`break` 这类**没有文字**的叶子：起始偏移 < cursor 就整体出现。从中间「切」对它们没有意义，所以「一揭示就整体出现」是自洽的（图片那条口径见 8.3）。**两侧都要判**：`start >= cursor` 或 `end <= 折点` 都丢掉——折点那一侧不判的话，一张已经翻上去的图仍然会渲染、并且仍然会去抓，与 8.2「只抓已经抽出来的那张」冲突。
- **内嵌 HTML 是例外：按「抽完才出现」判（`end <= cursor`）。** 原因是它的 `value` 里**连标签里的文字一起**——块级的 `<div>后面的话</div>` 在整个语法树里是**一个**节点。从中间切只会得到 `<di` 这种碎片（`tokenizeHtml` 认不出它是标签，会当普通文字吐出来，等于把裸源码字符弄上屏），不切就等于把未揭示的字一起放上屏。两条都不可接受，所以只有「等它抽完」这一条路。

  行内 HTML 的**文字泄露**问题不存在（remark 会把 `前文 <span>后面</span>` 切成 text / html / text / html 四个节点，文字本来就在 text 节点里、照常被截），**但这条规则对两类 html 节点一视同仁**：切开的 `<spa` 碎片同样会被当普通文字吐出来，所以行内的 `<span>` 也等它整个抽完才出现。这个分叉不值得按行内/块级判——一个空的 `<span></span>` 渲不渲染在屏幕上看不出差别，而分叉要多一次解析。

### 3.3 渲染只发生在渲染层，core 不动

本模块**不被 main 共享**，而 `src/core/` 的定义是「被 main 与 renderer 共享的纯逻辑」。另外整个 remark 生态都是 ESM-only（实测 `remark@15.0.1` 与 `remark-gfm@4.0.1` 的 `"type"` 都是 `module`；`remark-parse` 同族），放进 core 等于让 main 那份 `tsconfig.node.json` 也去解析它——多一类失败面，换不来任何东西。渲染层已经有 `src/renderer/src/state/shortcuts.ts` 这种纯模块的先例。

`src/core/bossKey.ts` 因此**基本不动**：它从「唯一的路」降级成「兜底的路」，见第 7 节。

### 3.4 屏幕上一辈子见不到裸记号

`**季度` 你抽到「季度」两个字时，它们**直接就是粗的**——解析器早就知道这一段是粗体。`#`、`**`、`|`、`>` 一个都不会作为字形出现。

这是 3.1 + 3.2 的直接推论：既然结构是预知的，记号就没有「先露出来再吃掉」的理由。要解决「记号看起来怪」，这一条是主刀。

### 3.5 阅读光标由语法树产出（2026-10-15 增补）

**光标画在「揭示到哪」那个字后面，而不是内容的末尾。**

`Page` 原来把 `<span class="wt-caret">` 追加在内容末尾。纯文本那条路内容是一串文字，它正好贴在最后一个字后面；但 `.md` 那条路的内容是**块级元素**的树，追加在末尾的 span 只能落在最后一个块**下方另起一行**——段落、列表、表格、代码块全都如此。而**隐形输入框与输入法候选框都按这个坐标摆**（`InputCapture.placeAtCaret`），所以这不是「光标画歪了」，是**候选框会飘**。

新口径：`renderMarkdown` 接一个「揭示到哪个偏移」，然后**按文档顺序走这棵树**，光标落在**第一个**符合下面任一条的位置：

> - 一个**带文本的节点**（`text` / `code` / `inlineCode`）**且区间 `[起点, 起点 + 长度]` 包含揭示偏移** → 把它的文本劈开，光标插在 `clamp(揭示偏移 − 内容起点, 0, 长度)` 处；
> - 一个**整个在揭示偏移之后**的节点（`起点 ≥ 揭示偏移`）→ 光标插在**它前面**；
> - 一个**跨过揭示偏移的叶子**（硬换行、图片、内嵌 HTML、脚注引用）→ 光标插在**它前面**；
> - **未揭示的占位**（表格、代码块底下那两块空白）→ 光标插在**它前面**；
> - 一条都没遇到 → **收进最后一块已渲染的内容**（2026-10-15 改；原先写的是「追加在末尾」，见下）。

**两条「插在它前面」不是冗余**：只看「起点 ≥ 揭示偏移」会**跳过提前渲染的叶子**（硬换行与图片的起点在揭示偏移**之前**，见下），只看「带文本的节点」又会漏掉**占位**与**块级容器**。

**表格的行与格要显式让路**（量出来的）：格里的文本节点自己会接住光标，而在**格/行**这一层开火会把光标插成 `<tr>` 的直接子元素——那不是合法的表格内容，CSS 会给它套一个匿名表格盒，**表格于是多出一列**（实测宽 115→172）。所以「插在它前面」只对**叶子**成立，容器一律往下递归。

**判据为什么是「结束偏移」而不是「起点」，这一条是量出来的、不是推的。** 有两类东西**提前渲染**：起点在揭示偏移**之前**、结束在之后——硬换行（`甲  ␊` 里那个 `<br>` 的区间从行尾两个空格起算）与图片（一揭示就整张出现，见 8.3）。只看起点会**跳过它们**，光标于是落到**下一行或图的右边**。实测（真管线 parse→clip→render）：

| 输入 | 揭示偏移 | 只看起点的落点 |
|---|---|---|
| `甲  ␊乙` | 2–4 | `<br>` 之后，即第二行 |
| `甲 ![图](…) 乙` | 3–19 | 图框右侧 |

**未揭示的占位走同一条规则**：它代表「还没到的东西」，所以**光标永远落在占位之前**。实测（同一张表）：揭示偏移 8–20 这**连续 13 个位置**上，旧判据把光标一路甩到占位**之后**——一张 20 行的表在行边界上会差出十几行的高。这一格不是观感问题：隐形输入框与候选框都按这个坐标摆。

**接受窗口的上界是「节点源码的结束」，不是「末行内容的结束」（2026-10-15 第三轮补）。** 这一格是**规格评审在 3.6.1 那批的返工里顺手扫出来的**：容器里逐行剥前缀的节点（引用块的 `> `、列表项的续行缩进），在**下一行还没开始**时，那段已经揭示的行前缀**不在任何一行里**——`clip` 的逐行表只收「起点 < 揭示偏移」的行，而前缀的偏移比它所属那一行的内容起点还靠前。于是这几个偏移位没有任何节点接得住，遍历走完一圈落到「一条都没遇到 → 追加在末尾」，**光标从块里跳到篇末**。实测（真管线 parse→clip→render，逐偏移扫三个夹具，探针跑在 `test-results/` 下的临时配置里）：

| 输入 | 揭示偏移 | 修前（实测） | 修后（按新判据推的，落地时实测复核） |
|---|---|---|---|
| `> 引用甲\n> 引用乙\n` | 6、7、8 | 篇末 | 段落内 |
| `- 甲甲甲\n  乙乙乙\n` | 6、7、8 | 篇末 | 列表项内 |
| `> <b>x</b>甲一\n> 乙二\n` | 7、8、9；13、14、15 | 篇末 | 段落内 |

**这三个夹具在 `12fac2d`（引进逐行偏移表之前）的那几格是在块内的**——但那是拿「顺带把还没揭示的字也显示出来」换的（实测 `'> 引用甲\n> 引用乙\n'`：揭示偏移 7 时旧版显示 `引用甲\n引`、新版显示 `引用甲\n`；偏移 8 时旧版是 `引用甲\n引用`）。所以这是**逐行偏移表带出来的真回归**，不是旧版本来就这样。修法两条，都在 `caretIndexIn` 里：**上界取节点源码的结束偏移**（末行内容之后到节点结束之间只剩语法——尾随换行、下一行还没揭示的行前缀），**落在这个区间的偏移一律给 `value.length`**。后者正是「没有逐行表」那条路给出的同一个数（那时末行长度本来就含尾随换行），两条路于是又合成一个；不这样做的话，同样的输入有没有逐行表会给出差一个换行的光标位置。

`clip` 的树形**一个字不改**：那几行前缀本来就该被丢掉（它们不上屏），该改的是「谁接得住光标」这条判据。

**但「修法两条」这个说法不完整（2026-10-15 落地时实测更正）**：第三行那个夹具（`'> <b>x</b>甲一\n> 乙二\n'`）的 `7、8、9` **不是**落在行前缀上——那几格落在 `clip` 把 `</b>`（「等整个抽完才留」）整条丢掉之后留下的**没有节点的缝**里，缝后面那个空文本节点起点是 10，被接受窗口的下界挡掉。实测：只做那两条改动，这三格**仍然掉在篇末**。第三处机制在 `renderAll` 的 text/html token 串上——本页最末那段「行内 HTML 那一段是个接受的近似」写的就是它（光标落在这段里时放在**这一段的末尾**，与「插在它前面」是同一个 DOM 位置，因为起点 ≥ 揭示偏移的节点必然渲染为空）。规格评审逐偏移验过它**不引入**多光标、不产生非法的父元素（18 份夹具 + 200 份定种子随机文档共 1988 格，三类违反都是 0），并且单独撤掉它时**只把光标从篇末搬回块内**（63 处），从未把已在块内的光标挪走。

三个推论都是刻意的：

- **落在空节点里也对**：列表项刚开始、文字还没出来时，那个空文本节点区间包含揭示偏移（起点 = 结束 = 揭示偏移），光标就落在序号后面——而不是掉到列表下方。这正是 3.2 里「打到了但文字还没出来」那一格要的画面。
- **落在记号中间也对**：`**季度**` 抽到第二个 `*` 时，`strong` 里的空文本节点接住它，光标落在粗体里面（下一个字要出现的地方）。
- **一个都没遇到**（揭示偏移落在文档末尾的换行之后之类）→ **收进最后一块已渲染的内容**（2026-10-15 改；原先是「追加在末尾」）。改的理由是那条兜底在**文档中间**也会开火：`clip` 把 `start >= to` 的节点**整块丢掉**，于是规则二（「整个在揭示偏移之后的节点 → 光标插在它前面」）对那些节点**永远开不了火**——它们根本不在树上。于是光标被追加成 `.wt-page__text` 的最后一个子元素，也就是**块下方**，而那个坐标是隐形输入框与输入法候选框的锚点（实测：14 夹具 230 格里，文档中间有 **15 格**这样，形态是多行列表的**每个项边界**、容器里的围栏、表格尾部、标题后的换行）。现在的做法是沿「最后一个孩子」走到链尾（最后一块已渲染的内容）：链尾带可裁文本就把偏移**夹**进它的区间，链尾是容器就追加在它最后一个孩子之后（**表格与表格行不挂**——光标成了 `<tr>`/`<table>` 的直接子元素会让表格多出一列，这条实测过）；**树上有占位时整条让路**，占位仍按「光标落在占位之前」自己接。回退到「追加在末尾」只剩两种情形：树上没有任何可接的内容，或者**链尾是内嵌/块级 HTML 这类叶子**（见下面那条已知残留）。

**行内 HTML 那一段是个接受的近似**：连续的 text / html 会被合并成一段 token 流渲染（理由见 `toReact.tsx` 的 `renderAll`），光标落在这段里时放在**这一段的末尾**。视觉上没有差别——揭示偏移之后的节点要么是空的，要么已被「`end <= to` 才出现」整条丢掉。

**已知残留：链尾是内嵌/块级 HTML 时，兜底仍会开火（2026-10-15 实施 4g 途中量出来的）**：`tailTarget` 对 html / 分隔线这类叶子返回空，于是那几格仍走「追加在末尾」——实测 `'甲 <b>乙</b>\n'` 的偏移 **7、8、9** 光标落在 `<p>` **外面**（本该在「乙」之后），`'甲\n\n<div>内容</div>\n'` 的 16、17 同理；300 篇语料里符合这个形态的约 **57 格**（代理判据：光标在块外、且它前面那块含内嵌 HTML 元素）。**「追加在末尾与放在它后面是同一个位置」这句话只对顶层的分隔线成立，对段落里的行内 HTML 不成立**——修法要能区分「渲染成真盒子的叶子」与「渲染成行内标记的 html」，本轮不做，记在验收清单里由用户定。

**`Page` 在 md 那条路上不再追加末尾那个 span**，纯文本那条路一个字不变。

### 3.6 代码类节点的 `value` 起点（2026-10-15 修一处既有缺陷）

**缺陷**：`clip.ts` 原来按「`value` 的第 n 个字符 = 源码偏移 `position.start.offset + n`」切代码。这对 `text` 成立，对 `code` / `inlineCode` **不成立**——mdast 的 `position` 从**定界符**起算，而 `value` 里不含定界符：

```
源码 '```\n第一行\n第二行\n'    position.start.offset = 0   ← 第一个反引号
                               value = '第一行\n第二行'      ← 没有围栏、没有语言标注
```

实测（跑真实的 `clipTree`，不是推的）：光标走完 ` ``` ` 那一刻、正文一个字都没揭示时，**第一行已经整行上屏**；光标走到第二行中间时**三行全在**。内容是**恒定领先光标 4 个字符**——正好是 ` ``` ` 加换行的长度（带语言标注时是 6）；行内代码领先反引号的个数。这直接违反「不显示任何未揭示的字符」，而且**零覆盖**：`markdownClip.test.ts` 里一条 `code` 类型的断言都没有。

**为什么现在必须修**：3.5 那条要求光标精确落在代码块**内部**，靠的就是这套映射；不修的话光标进了框、位置仍差 4 个字符。

**修法**：在 `parse.ts` 里为每个 `code` / `inlineCode` 节点记下 `value` 的**真实源码起点**。算法**不是「跳过定界符」，而是「`value` 首行所对应的那一源码行的行尾，往前退 `value` 首行的长度」**——容器前缀（引用块的 `> `、列表项的缩进）、围栏自身的缩进、代码块的缩进，全都只是「更靠左的前缀」，被这一步一并盖住。`clip.ts` 用它当裁剪原点，3.5 的光标也用它。**`parse.ts` 是全仓唯一手上有源码的地方**，所以这个映射由它算一次、挂在节点上。

**标注的语义是「这个节点当前的 `value` 的第一个字符在源码里的偏移」，所以裁剪之后要跟着挪。** `clip.ts` 切片时把起点后移切掉的那一段（`head`）。不挪的话，裁剪后的树上会带着一个**失真**的起点——而设计 3.5 的光标正是按「揭示偏移 − 内容起点」算位置的，那种错**不报错**，只是光标差几个字符。（Task 2 的质量评审量出来的：切过之后读到的是原始的 4，而 `value` 已经后移。）

（这一版是返工后的。第一版按形态跳前缀——「围栏 = 首行换行之后、缩进块 = 首行缩进之后」——只对**顶格**围栏精确：容器里的代码块会让内容**提前** 2–4 个字符（引用块 −2、列表项 −2/−3、两层嵌套 −4），五格以上缩进的块会让它**晚** 4 个字符，两个方向都错。是质量评审判为「必须改」才换掉的，换完 28 组输入全部归零。）

**残留清零了（2026-10-15 第二轮，用户裁定「现在修」）。** 这里原先记的是「带前缀的代码块，内部各行仍差一个前缀宽度，不为它做逐行映射」。那条裁定被推翻了，理由见下面 3.6.1：**同一套坏坐标也落在容器里的普通文字上，而且方向是提前**（比代码块那条更严重）。修法是一次做的，代码块那两处残留（缩进块、带缩进的围栏）也一并精确。

### 3.6.1 逐行偏移表（2026-10-15 第二轮）

**起因是质量评审在光标返工里顺手量到的**：容器里**逐行剥前缀**的文字——引用块的 `> `、多行列表项的续行缩进——`value` 的下标与源码偏移**不是差一个常量**，第二行起每行差一个前缀宽度。实测（用仓库里的 remark 复算，不是推的）：

```
源码 '> 引用甲\n> 引用乙\n'
text 节点  position = [2, 11]，value = '引用甲\n引用乙'（长度 7）

揭示偏移 7 时屏幕上是 '引用甲\n引'，而 0..6 已揭示、去记号后是 '引用甲'
→ '引'（源码偏移 8，还没揭示）漏上屏了，差的正是 '> ' 那个宽度
```

方向是**提前**——直接违反「不显示任何未揭示的字符」。它**连带**污染光标：3.5 的落点用「揭示偏移 − 内容起点」算字符位置，而那个减法只在**行内**成立。

**修法：给这类节点挂一条逐行偏移表**（`wtLineStarts`：每个 value **行**的首字符在源码里的偏移，一行一个数）。它成立的依据是 3.6 那条技巧的推广——**每一行的 `value` 都贴在该行源码的尾部**，前缀（`> `、缩进、围栏）全在它前面：

```
行 k 的源码起点 = 该行源码的结束偏移 − 该行在 value 里的长度
```

于是 `clip.ts` 改成**逐行取「与 `[from, to)` 相交的那一段」**（行内仍是 +1 线性，所以逐行就够），`toReact.tsx` 的光标也照它把揭示偏移换算成 value 下标。**顺带**：3.6 上面那两条残留走同一条路一并精确——它们的 `value` 同样是逐行剥出来的，此前只修了首部。

**上面那条算式是错的（2026-10-15 第三轮改）。** 「每一行的 `value` 都贴在该行源码的尾部」只说对了一半：remark 剥的不只是**行首前缀**，还有**行尾空白**。于是「行尾 − 行长」把被剥掉的字也算进去了，整张表往后偏。实测：

| 源码 | `value` | 「行尾 − 行长」 | 真值 |
|---|---|---|---|
| `甲 \n乙\n` | `甲\n乙` | `[1, 3]` | `[0, 3]` |
| `> 甲 \n> 乙\n` | `甲\n乙` | `[3, 7]` | `[2, 7]` |
| `> 甲 \t\n> 乙\n` | `甲\n乙` | `[4, 8]` | `[2, 8]` |

方向是**晚**——与下面记的那条「行内代码差 1」同向、与 3.6.1 要治的那条（提前）相反，后果是那一行的首字**晚一个按键上屏**（真管线实测：顶层 `'甲 \n乙\n'` 在 `to = 1` 时旧版显示 `甲`、现在显示空）。这是 4b 带出来、当时就在线上的回归。

改法是**回验**：在该行源码里找那行文字**最后一次**出现的位置（行尾空白是它后面唯一允许多出来的东西），并要求其后到行尾**全是空白**。

**回验对不上时怎么办——「不挂表」那条写法是错的（2026-10-15 第四轮改）。** 这里原先写的是「找不到就**不挂表**，退回『起点 + 字符数』那条路——宁可少精确一处」，把退路定性成**精度问题**。实测它是**方向问题**：不挂表之后 `clip` 退回按字符数切，而容器节点的裁剪原点是**首行**的内容起点，于是从第二行起每一行的前缀宽度都变成**提前量**，**屏幕上会出现还没揭示的字**。改法是**回验失败也不摘表，退回恒不提前的保守算式** `lineEnd − line.length`——理由与实测见本节末与文末第四轮那条。

**表的长度可能比 `value` 的行数少一行（2026-10-15 第三轮补）。** `clip` 把末行那个**换行**算进 revealed（理由见下），于是切出来的 `value` 会多出一个**空行**；而表里只有「起点 < 揭示偏移」那几行的起点。实测（6 个夹具逐 `to` 扫）：`'> 引用甲\n> 引用乙\n'` 在 `to=6` 上是 `value='引用甲\n'`、表 `[2]`；`'> 甲\n> 乙\n> 丙\n'` 在 `to=8` 上是 `value='甲\n乙\n'`、表 `[2,6]`。**多出来的那一行恒为空行**（两份独立扫描都只见到这一种）。所以读表的那一侧（`toReact.tsx` 的 `rowsOf`）**行数由 `value` 定、表只供 `src`**——它原来那句注释「切后的 `value` 有几行，表就有几个数」不成立。

**不做的事**：不为行内再做更细的映射（行内连续，本来就精确）；不为转义/实体做映射（3.6 已记的那条近似不变）；`inlineCode` 那个 1 字符的偏差也不在这条路上（理由见下）。

**行内代码另有一处 1 个字符的偏差，一并记在这里**：CommonMark 剥的是内容两侧的**空白**（不只是空格），所以用换行垫的那种写法 ` ``\n甲\n`` ` 的 `value` 是 `甲`，而现在的判据只认空格、按定界符算起点，差 1。这个形态在工作文档里基本不出现，修它要么放宽判据要么走逐字符回验，都不值当，所以留着——**但它是往「提前」方向差的**（1 个字符），与上面那条方向相反，别混为一谈。

**行内代码是单独一支**，因为 CommonMark 会在两侧**各剥一个空格**（`` ` 甲 ` `` 的内容是 `甲`）：「跳过起首反引号」与「按收尾反引号往回退」两种写法都会差 1。现在用的是**带 `value` 回验**的版本——先按定界符切出 `raw`，`raw === value` 就直接用，否则在「两侧各是空格且 `raw.slice(1, -1) === value`」时取 `from + 1`，再否则退回 `from`。六组实测全中。（跨行的行内代码 remark 保留换行、不折空格，所以那种写法也能精确命中。）

## 4. 语法表（渲染到哪一档）

用户选的是**全套 CommonMark + GFM**。逐项落到渲染：

| 语法 | 渲染成 |
|---|---|
| 标题 1–6 | Word 内置「标题 1/2/3…」的样子，字号递减，深蓝加粗 |
| 粗体 / 斜体 / 删除线 | 对应的字形与颜色 |
| 行内代码 | 等宽 + 浅灰底 |

| 任务列表 `- [x]` | **不可点**的方框（文档运行期只读、永不修改，见既有硬规则） |
| 引用块 | 左侧竖线 + 灰色文字，可嵌套 |
| 分隔线 | 一条细横线 |
| 链接 | 像链接（蓝 + 下划线），**点了不做事**（见 9.3） |

**不做语法高亮**是刻意的：一份「Word 文档」里的代码块本来就是一块等宽字，加了配色反而更像编辑器、更不像文档。

## 5. 渲染管线

```
flatText ──remark-parse + remark-gfm──▶ mdast（带 position.offset）
                                          │  解析一次，按文档缓存
                                          ▼
                              clip(mdast, revealStart, cursor)
                                          │  每次渲染都跑，纯函数
                                          ▼
                         mdast-util-to-hast ──▶ hast
                                          ▼
                              rehype-sanitize（白名单）
                                          ▼
                              rehype-react ──▶ React 元素
```

**解析只做一次。** 200KB 的 md 解析是几十毫秒量级，每次按键重解析不可接受。缓存挂在 `App` 里，键是工作文档那个 `Novel` 对象——它一旦变（重新导入、移除）缓存自然失效。

裁剪之后的那一段很小（大约一页），所以后面几步每次渲染重跑是可以接受的。

**全仓不出现 `dangerouslySetInnerHTML`。** 内嵌 HTML 那一路也走「解析成节点 → 映射成 React 元素」，不把字符串塞进 DOM。这条是硬规矩，不是风格偏好。

## 7. 铺满的语义变更

老板键的「铺满一页」现在按**字符数**算：`CHARS_PER_SHEET = 1330` 是拿纯文本推的（626px 宽 ≈ 41.7 字/行 × 32 行）。渲染之后这个数不准了——记号被吃掉不显示、标题字号更大、列表有缩进、表格有边框，同样 1330 字占的高度差很多。

**新口径：按渲染后的真实高度铺，且停在块边界。**

```
1. 目标高度 = bossFillPercent% × 纸张正文区高度
             （从 .wt-page 的计算样式量出来，不写死 912）
2. 离屏渲染整份文档（每个顶层块套一层带 `data-block-end` 的包装），
   从 DOM 自己读回「块的结束偏移 + 高度」
3. pickFillCut(块高表, 目标高度) → 字符偏移（纯函数）
4. engine.revealTo(切点)
```

**两处与最初写法不同的地方，都是实施时量出来才改的：**

- **偏移从 DOM 自己读，不吃一个外部数组。** 原来打算把偏移单独算一份传进去，但那样「有几个块」是两处各自决定的，永远能对不上——`definition`（`[a]: url`，真 md 里很常见）与只含注释 / `<script>` 的 HTML 块都渲染出**零个 Element**，DOM 于是比「块」少一个。后果是**整篇静默退回按字符数铺**：不报错、不白屏，只有真机上铺不满才看得出来。现在每个顶层块在渲染时套一层带 `data-block-end` 的包装，一一对应由构造保证。
- **高度取「下一个块的 offsetTop − 这个块的 offsetTop」，不是 `offsetHeight`。** 相邻块之间的外边距会**折叠到包装元素之外**，`offsetHeight` 量不到那一段，按它累加一页会少算几百像素。

**关于「量到目标高度的 2 倍就停」：这条没做。** 隐藏副本渲染的是整份文档。功能上不算错（`pickFillCut` 反正会提前 `break`），但几十页的文档进老板模式要先整份渲染一遍——那是一次真实的卡顿，**记在这里而不是假装做到了**。要治它得让副本分片渲染，那是另一个功能的体量。

「停在块边界」的意思是：切点落在某个块的结束偏移上，**不切行、不切表格、不切引用块**。屏幕底部因此永远是一整块，不会出现半句话或半张空表格。

**逐行揭示对这条没有影响（2026-10-15 补）。** 理由反直觉，所以写下来：切点是**某个块的 end**（`pickFillCut` 返回 `b.end`），而 `revealTo` 设的是 `cursor`（`engine.ts`）——于是老板模式里可见窗口是 `[revealStart, 切点]`，最后一个块的 end 正好等于 cursor，**那个块是完全揭示的**。也就是说，铺满的可见页里根本不存在「未揭示的行/项」，整页高度与量出来的高度一致，切点照旧算得准。3.2 那次修订不需要给铺满加任何补偿。（这条只在代码上推过，没有跑；依据是上面两个返回值，以及 `clipTree` 对 `end == to` 取等这一条——后者有现成用例钉着。）

**`bossFillPercent` 的含义从「一页字符数的百分比」变成「一页高度的百分比」。** 100% 仍然是「刚好一页」，只是这个「一页」从估的变成量的。

**两条兜底，都必须有：**

1. **第一个块就超过一页** → 铺满那一个块。宁可溢出一页，也不能铺出一张白纸。
2. **量不出高度**（jsdom 里 `offsetHeight` 恒为 0，或测量抛错）→ **退回按字符数**，用的还是 `CHARS_PER_SHEET` / `fillCharsFor` 那一套。

所以 `src/core/bossKey.ts` 的逻辑**原样保留**，只是从「唯一的路」降级成「兜底的路」。两个好处：core 那批逐字节围栏与单测基本不用动；这条降级路径在 jsdom 里是**可测的**，否则「量高度」整块就是零覆盖（`tests/` 跑的是 jsdom，没有布局）。

**块高表的生命周期：** 进入老板模式时量一次；`⌘⇧↑` / `⌘⇧↓` 只重算切点，不重量（文档没变，块高也不变，变的只是目标高度）。重新导入或移除工作文档时丢弃。

## 8. 图片

### 8.1 两条来源，一条通道

渲染层是沙箱（`sandbox: true`），读不到磁盘、也不该自己联网。两种图片都经**同一条 IPC** 由主进程取回来，交给渲染层的都是 `data:` URL：

| 来源 | 主进程怎么做 |
|---|---|
| 本地路径 | 按工作文档所在目录解析相对路径，读文件 |
| `http:` / `https:` | 主进程去取 |

**基准目录由主进程自己算**，不接受渲染层传进来的路径：主进程从设置里读 `workDocPath`，取它的 `dirname`。这样渲染层能请求的东西被限定在「工作文档相邻的位置 + 网络」，而不是「任意基准目录」。

**CSP 一个字不改。** `img-src 'self' data:` 本来就允许 `data:`，所以这条通道走完，CSP 完全不用碰——这也正是选「主进程代取」而不是「放开 CSP」的理由（那个 meta 上面挂着一段警告注释，位置是承重的）。

### 8.2 抓取时机

**只抓已经抽出来的那张。** 图片节点被揭示（起始偏移 < cursor）的那一刻才请求，文档里没被抽到的外链一次也不会被访问。

### 8.3 出现时机

**一揭示就整张出现**（用户拍板）：不等 `](路径)` 抽完，路径还没抽完时图就跳出来。这与 3.2 是同一条规则——已经开始的东西，画完整的。

### 8.4 上限与失败

- 只接受 `image/*`，**超过 8MB 的拒绝**；网络请求 10 秒超时
- 失败（路径不存在、超时、不是图片、超限）→ 渲染层显示**占位框 + 替代文字**，不弹错、不打断
- 渲染层按「解析后的绝对来源」缓存拿到的 data URL，避免每帧重发 IPC

## 9. 三处具体的渲染口径

### 9.1 脚注

`[^1]` 显示成**上标**，内容是 label 原文（惯例上 label 就是数字，所以与「上标数字」等价）；脚注定义**按它在源文件里的位置**渲染成一个带标号的段落——惯例上这些定义本来就写在文末，所以看起来就是文末的一组脚注。

**「收在正文末尾一个『脚注』小标题下」这条做不到，这里如实改掉：** 那要求把定义**从源位置搬到末尾**，而整个模型是「按位置揭示」的——搬动意味着渲染顺序与源顺序不一致，屏幕上那一段就不再是 `flatText.slice(revealStart, cursor)` 的呈现，核心不变量当场破掉。收益只是「更像惯例」，不值得。

**不照 Word 的页面底脚注**：那需要「页面底部」这个概念，而本应用的纸是一张**连续变长的长纸**（`min-height: 1080px`，内容多了就长高），没有页面边界可言。硬造一个出来要额外的布局机制，收益只是更像 Word 一点点。

### 9.2 表格

宽度固定为正文宽（626px），单元格里的字自动换行，**不出现横向滚动条**——真 Word 也不横滚。列多的表会被压窄，这是接受的结果。

**逐行揭示**（2026-10-15 加）：光标走到第几行，第几行才画出来；还没走到的行只在表格底部留「默认一行高 × 剩余行数」的空白，**不画那几行的网格线**。一行的单元格整体出现（理由见 3.2），所以表格永远不会出现缺列的残行。

### 9.3 链接

样式像链接（蓝色 + 下划线），**点了不做事**。点开链接会拉起系统浏览器——一个伪装成 Word 的应用突然开浏览器，副作用太显眼，收益又接近于零（工作文档里的链接多半是内网地址或文档引用，本来也打不开）。

## 10. 样式

Word 风，逐项对齐 Word 内置样式：

- **标题**：微软雅黑 / 等线加粗，标题 1 用 Word 默认的深蓝 `#2F5496`，2/3 级依次减小字号、同一色系
- **正文**：继承现有 `.wt-page` 的字体（Georgia / 宋体系）
- **列表**：Word 的项目符号（`•`）与编号，缩进对齐
- **引用**：左侧 3px 竖线 + 灰色文字
- **代码块**：浅灰底 + 等宽 + 内边距；行内代码同色系、更小的内边距
- **表格**：细网格线（Word 的「网格型」），表头加粗
- **分隔线**：一条 `1px` 细横线

**所有颜色走 CSS 变量**，深色主题与「深色下纸张也变暗」两个开关都要跟着走——本仓库在这个坑上栽过（`color-scheme` 与主题变量是两套东西，滚动条与原生控件归前者管）。标题那个深蓝在深色下必须给一个亮一档的替身，否则在暗底上几乎看不见。

## 11. 安全边界

用户选的是「只渲染安全的排版标签」。具体口径：

- **白名单标签**：`br` `b` `strong` `i` `em` `u` `s` `del` `sub` `sup` `span` `div` `p` `code` `pre` `small` `mark` `hr`
- **属性一律丢弃**，包括 `style` / `class` / `id` / 一切 `on*`。丢 `style` 是刻意的：留着它等于让文档控制页面的外观，而外观是这个应用用来伪装的东西
- **白名单之外的标签**：标签本身丢掉，**里面的文字按普通文字保留**（`<script>alert(1)</script>` 显示成 `alert(1)`）。它永远不会被执行，因为整条路都不碰 `innerHTML`
- **HTML 注释（`<!-- … -->`）整段丢掉**。它是写给作者看的，不是内容；不丢的话会原样成为屏幕上的字面文字（注释不是标签，标签匹配式够不着它）
- 整条渲染路径**不出现 `dangerouslySetInnerHTML`**（第 5 节）

**这条白名单挡住的是一条真实的链**：工作文档里的 HTML 若能带事件属性执行，它就在一个握着 `window.api` 的渲染进程里跑——而 `window.api` 上有导入小说、写设置、以及第 8 节那条读本地图片的通道。挡住执行面，「读文件」那条通道的暴露面就降回「图片能被读出来」这一档。

## 12. 错误处理与边界

| 情形 | 行为 |
|---|---|
| md 解析抛错 | 退化成**现有的纯文本路径**（同一个 `visibleText` 渲染），`console.warn` 一行。**不许白屏** |
| `.md` 里其实全是普通文字 | 正常——渲染出来就是一串普通段落，与今天肉眼看不出差别 |
| 图片读不出 / 超时 / 不是图片 / 超限 | 占位框 + 替代文字（8.4） |
| 量不出块高 | 退回按字符数（第 7 节兜底 2） |
| 第一个块就超过一页 | 铺满那一个块（第 7 节兜底 1） |
| 文档很大 | 解析一次并缓存；测量要把整份文档离屏渲染一遍（第 7 节：分片测量**没做**，那是已知的卡顿，别以为这里写了就是做到了） |
| 折叠条（`RENDER_WINDOW_LIMIT = 30000`） | md 这边按**块边界**切：从末尾往前累加各块的**字符长度**，到 30000 为止，取那个块的起始偏移作为折点。**不复用 `pickFillCut`**——那个函数吃的是高度，折叠这一步没有（也不该有）布局信息 |

## 13. 对既有代码与文档的改写

1. **核心不变量要改写。** `CLAUDE.md` 现在写的是「阅读区显示的内容恒等于 `flatText.slice(revealStart, cursor)`」。渲染之后 `#`、`**`、`|` 是字符但不当字形显示，所以要改成：

   > 阅读区**显示出来的文字**，等于已揭示那一段（`flatText.slice(revealStart, cursor)`）**去掉语法记号之后**的文字；此外不显示任何未揭示的字符。结构骨架**逐层按起始偏移给**：块开始了才画这个块，表格的行、列表的项也是一行/一项开始了才画；没开始的部分只占高度（或干脆不占），**不含任何未揭示的字符**。

   **小说那条路与 `.txt` 工作文档一个字不变**，改写只落在 `.md` 那一路。`CLAUDE.md` 里那句要写清这个分叉，否则下一个读它的人会以为不变量整体失效了。

2. **`src/core/bossKey.ts` 的注释**：`bossFillPercent` 的含义从「一页字符数」变成「一页高度」，`CHARS_PER_SHEET` / `fillCharsFor` 变成兜底。改的是注释，逻辑不动。

3. **实现计划的逐字节围栏**：本仓库的硬约定——动了源码（含只改注释）就要把 `docs/superpowers/plans/` 里对应的围栏同步回写，口径是 `md5(围栏原始内容) == md5(文件)`。本功能会动 `App.tsx` / `Page.tsx` / `bossKey.ts` / `ipc.ts` / `channels.ts` / `preload` / `global.d.ts`，这些都在 06 那份正本里有整文件围栏。

4. **新依赖**：`unified`、`remark-parse`、`remark-gfm`、`mdast-util-to-hast`、`rehype-sanitize`、`rehype-react`，以及 devDependency `@types/mdast`。全部是 ESM-only，**只允许渲染层引用**（`unified` 是用来把前两个串起来的那个壳，`remark` 元包本身不需要）。

## 修订记录

### 2026-10-15 —— 结构预知的粒度从「块」下沉到「重复单元」

**改了什么**：3.2 那条「块一开始，它内部的结构就整块画出来」收窄成「块内的表格行、列表项各自按起始偏移判」。块一级的规则一个字没动。

**为什么改**：真机上看到的效果与原意不符——块一露头，整张空网格、整个列表的全部符号、代码框的底色在**那个块还没被读到时就全铺出来了**。用户的原话是「太拥挤」，要的是「打字打到哪里渲染到哪里」。

**逐条拍板**（都是用户看过预览图之后点的）：

| 问题 | 结论 |
|---|---|
| 按什么粒度判「打到哪里」 | 逐行逐项：表格逐行、列表逐项、代码块逐行 |
| 没揭示到的部分占多少高度 | 表格与代码块占「默认一行高」；**列表完全不占** |
| 占位部分画不画外框 | **不画**，只留白——表格不画空网格线，代码块不画空框 |

**没有改的**：行内结构的粒度（理由见 3.2）、块一级的判据、「未揭示的字符一个都不上屏」、铺满那一路（理由见第 7 节）。

**一处要连带改的旧文字**：实现计划末尾那条验收项「抽到表格表头那一刻，整张网格就画出来了」描述的正是旧行为，本次修订后不再成立——由新的实现计划替换掉它。

### 2026-10-15（第二轮）—— 阅读光标进树，以及代码块偏移的缺陷

用户真机验收时发现两件事，一起修。

**其一：光标不在块里面，在块下面。** 诊断与口径见 3.5。这不是观感问题——**隐形输入框与输入法候选框都挂在这个坐标上**，光标离得越远候选框飘得越远。修法是光标改由语法树产出，`Page` 不再追加末尾那个 span。

**其二：代码块的 `value` 与源码偏移不是同一个坐标系。** 见 3.6。`code` / `inlineCode` 的 `value` 不含定界符，而原实现按 `position.start.offset` 切，于是**内容恒定领先光标 4 个字符**（实测：光标走完围栏那一刻第一行已整行上屏）。用户最初的观察是「代码块好像没问题」，量过之后确认有——恒定 4 个字符的领先量很难靠肉眼发现。这条与 3.5 耦合：光标要精确落在代码块内部，就得靠这套映射。

**这一轮新拍板的**：

| 问题 | 结论 |
|---|---|
| 光标画在哪 | 由语法树产出，落在「揭示到哪」那个字后面（3.5 那条规则） |
| 代码块偏移缺陷 | **修**，只修首部偏移；四空格缩进块的逐行偏差记在 3.6 里不修 |
| 光标命中不了任何文本节点时 | 退回旧的「追加在末尾」（此时内容本来也到头了） |

**第一轮那三条在没有让步**：逐行逐项、占位只留白、列表完全不占位——本轮一个字没改。

### 2026-10-15（第三轮）—— 逐行偏移表的三处修正

**起因是评审发现的、不是用户报的**：Task 4b（逐行偏移表）交付后，规格评审与质量评审各查出一批。这一轮一共三件：

1. **光标在容器的行前缀上掉出块外**（3.5 末尾）——它与用户最早报的「光标不在代码块里面」是**同一个缺陷类**，只是一个在行级、一个在偏移级。
2. **行尾空白被 remark 剥掉时整张表右移**（3.6.1）——**这一条是当时就在线上的内容回归**：`Page.tsx` 早就接了 `MarkdownView`，内容那一半是活的（只有 `caretAt` 还没接），表现为那一行的首字晚一个按键上屏。
3. **表的长度比 `value` 的行数少一行**（3.6.1 末段）——它是第 1 条的根因之一，同时让 `rowsOf` 的注释成了假话。

**为什么第 1 条必须现在修**：下一批的接线（`MarkdownView` 传 `caretAt`）一落地它就会露出来，而那一步的验收判据正好压在这几个偏移上。修法落在 `caretIndexIn` 与 `rowsOf` 两处，**不动 `clip` 的树形**——那几行前缀本来就该被丢掉，该改的是「谁接得住光标」。

**评审实测否掉了一个看着显然的修法**：上界写成「末行内容结束 + 1」**不够**——窗口在源码那一侧一直伸到下一行的内容起点，中间还隔着 `> ` 那两个字符，实测掉出集合只各减一个（`6` 修好了、`7` 与 `8` 还在）。所以上界取**节点源码的结束偏移**。

**零覆盖的守卫一共四处**（评审逐条回退量出来的），取舍各不相同：

- **`clip.ts:224` 的空窗口守卫与 `clip.ts:244` 的陈旧表删除是真的漏洞**：可达、**会改变光标落点**（前者：`'> ```\n> 甲\n> 乙\n> ```\n'` 的 `to=2` 从 `BLOCKQUOTE` 落进 `BLOCKQUOTE>PRE>CODE`；后者：`'甲 \n乙\n'` 的 `to=1` 从根节点挪进 `<p>`），却一条用例都不看着它们。由 4e 用一条「不许挂表」的断言同时堵上——**但要钉在「空窗口那一格」上**，「空 `value` 一律不许挂表」那条不变量在基线上是假的。
- **`holdsCaret` 那条意义弱得多**：评审判它是一次**行为等价**的去重——新老两版在现有夹具上**输出完全一致**，差异只在「值节点会不会压住 `caretBefore`」那一支，而那一支在那些位置本来就不开火。所以「换回算术版一条都不红」是**预期**，不是漏洞。4d 放宽上界之后两版**可能不再等价**，那时这条变异正好当探针（不红就照实报告，不拿改断言去凑）。
- **接受窗口那个 off-by-one** 由 4d 里三条「落在行前缀上」的用例守着。

### 2026-10-15（第四轮）—— 退路的方向：摘表会让未揭示的字上屏

**起因是规格评审，不是用户报的**：3.6.1 里「回验对不上就**不挂表**……宁可少精确一处」这句把退路定性成**精度问题**，实测它是**方向问题**——不挂表之后 `clip` 退回按字符数切，而容器节点的裁剪原点是**首行**的内容起点，于是从第二行起**每一行的前缀宽度都变成提前量**，**屏幕上会出现还没揭示的字**。这是核心不变量（不显示任何未揭示的字符）被破。

**实测**（评审，10 个转义/实体夹具逐偏移扫；夹具 `'> 甲 &amp; 乙\n> 丙\n'`，`丙` 在源码偏移 14）：`to = 6` 显示 `"甲 & "`（真值 `"甲"`）、`to = 9` 显示 `"甲 & 乙\n丙"`（真值 `"甲 &"`）、`to = 12` 显示整条（真值 `"甲 & 乙\n"`）。泄漏计数（判据是「屏幕上显示的整段文字能不能在 `src[0, to)` 里**按序匹配**出来」，不依赖人眼）：**79 格**。

**触发条件是回验失败**：`value` 与源码不是逐字相同（HTML 实体 `&amp;`、反斜杠转义 `\*`），或该行文字**在文档前文出现过**（`lastIndexOf` 找到别处、被下界挡掉）。**仓库语料碰不到**（13 个 `.md`、14161 个带 `value` 的节点上 4b 与 4c 的表 0 差异），所以这条只能靠夹具守。

**修法**：回验失败时**不摘表**，退回**恒不提前**的保守算式 `lineEnd − line.length`；**只对 `value === ''` 保留不挂表**（第三轮那条——空值没有内容可泄漏）。

- **「恒不提前」可证**：`value` 行是源码某连续片段的解码结果（剥前缀把片段起点**右移**，剥行尾空白与解码只让它**更短**），所以 `line.length ≤ 该行源码内容长度` ⇒ `lineEnd − line.length ≥ 真实内容起点`。评审用一支**不复用 `buildLineStarts` 任何逻辑**的独立对齐器在 42808 行上验过：**违例 0**。
- **代价是左端晚**：那一行的首字晚若干按键上屏，晚的格数**等于该行记号的超出量**（`&amp;` 是 4、`\*` 是 1、`&nbsp;` 是 5），`to` 够大之后与真值逐格一致。**两害相权：晚是「少显示」，提前是「多显示」。**
- 泄漏计数 **79 → 0**；提案版与 4b 那版在这批夹具上**逐格相同**（合理：4b 用的就是这个算式，区别只在「回验成功的行用精确值」）。

**连带两处**：`parse.ts` 那两句「找不到就不挂表——退回『起点 + 字符数』那条路」成为假话，要一并改；以及下面这一格。

**「光标窗口左端掉出容器」那条预测，实测不成立（2026-10-15 补正）。** 这里原先写的是「换成有表之后……『光标掉出容器』的窗口从右端搬到了左端（**实测**：`to = 3..6` 从块内变成篇末，`to = 15` 反过来修好）」——**那句话是把评审的预测当成了实测**（我写的，不是量的）。实测（10 个夹具 × 全部偏移，逐格差分 `945c7b5` 与 `31d9813`）：**没有任何一格**改变容器归属，`to = 0` 与文档末尾那两格两版相同；唯一的变化是**屏幕少显示几个字**（转义/实体那一行的首字晚 2–4 个按键，`to` 够大后逐格追平）。机制上也说得通：有表时 `clip` 只收「窗口与 `[from, to)` 相交」的行，所以 `rows[0].src < to`；表被摘掉时退化行的 `src` 就是 `originOf(node)`。**候选修法（下界改取 `originOf`）逐格与交付版字节相同**——换了等于没换。

**但「下界是死代码」这句话只对那个候选修法成立，对整个删掉不成立（同批实测）**：把下界**整条删掉**全仓 592 条仍绿，然而**行为不等价**——它与交付版**逐格差 39 格**（`fence_top 1–3`、`fence_top2 1–3`、`fence_in_quote 1–7`、`fence_in_quote_tail 1–7`、`fence_in_list 1–7`、`fence_empty 1–3`、`fence_empty_tail 1–3`、`indent_code 1–3`、`indent_code_tail 1–3`）：那些格是**`value` 为空、内容起点却在揭示偏移之后**的代码节点（围栏正在被敲的那一段），下界把光标拦在了元素外面（落到篇末），删掉它光标才进得去空 `<pre><code>`。**「全绿」是覆盖事实，不是等价事实**——这两件事在计划与提交信息里被并成了一句。那 39 格在 `945c7b5` 上完全相同，属于本批更早一处改动留下的既有形态，不是这一轮带出来的；第三轮那条接受窗口的保护对象（「值节点不抢它前面的光标」）与 `rows[0].src` 在空节点上不是同一个数，要窄修得看 `position.start.offset` 那一侧，**改前必须实测**。
